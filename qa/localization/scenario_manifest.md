# Localization Step 7 Scenario Manifest

Status: `MANUAL ACCEPTANCE NOT STARTED`

The 45 prepared scenarios remain available QA infrastructure. The former checklist-ID column below is historical scenario capability/provenance only; it is not the formal Step 7 contract. Formal localization-delta routing is exclusively defined by `execution_guide.md` Appendix A.

All paths and commands are project-relative. Every production app root is exactly:

`outputs\localization_step7_runtime\<scenario>\localappdata\ProbabilityCalibrationTool`

The preparer accepts only the fixed scenario names below. Before every reset/write/mutation it validates the project-controlled runtime root, allowlisted unresolved immediate child, resolved containment, real-default-root exclusion, and every relevant nested symlink/junction/reparse component. It never uses network access. Reset only removes a reparse-free whitelisted scenario tree.

## Common commands

- Strict QM: `uv run python tools/localization_step7_prepare.py compile-qm`
- Prepare all: `uv run python tools/localization_step7_prepare.py prepare all`
- Safety guard: `uv run python tools/localization_step7_prepare.py safety-check`
- Inspect paths/launch: `uv run python tools/localization_step7_prepare.py show <scenario>`
- Nonvisual fixture probe: `uv run python tools/localization_step7_prepare.py probe <scenario>`
- Ordinary real entrypoint: `$env:PYTHONPATH='src'; $env:LOCALAPPDATA=(Resolve-Path 'outputs\localization_step7_runtime\<scenario>\localappdata').Path; uv run python -m probability_calibration_tool`
- Fault launch: `uv run python tools/localization_step7_prepare.py launch <scenario>`

The fault launcher prints `TEST-ONLY MANUAL QA FAULT INJECTION` and the exact seam. It still composes the real production bootstrap, DesktopHost/session, and production windows; it creates no substitute UI.

## Scenario semantics

- `healthy_en` and `healthy_zh`: character 1 has 50 included wins and 50 included losses (numerical historical reference ready); character 2 has one included win (insufficient history); another character supplies no eligible history. The human creates fresh pending/completed states through the GUI.
- `restore_normal` and `restore_normal_en`: live state A has completed rows for characters 1 and 2. Candidate B has only character 1. The Maintenance counts provide a harmless visible distinction after real restore.
- `restore_corrupt`: the recognized corrupt file is intentionally excluded from the verified-candidate list; the human inspects that production behavior.
- All `data_safety*`, both `multiple_pending*`, and damaged-live Emergency fixtures remain abnormal. Startup must not normalize them.
- `recovery_no_pending`, `recovery_no_pending_zh`, `restore_invalid`, and `emergency_invalid` change only the isolated fixture after the production page/selection exists. These are not production fault injectors.
- The preparer never performs Correction, Normal Restore, or Emergency Restore. Those transactions remain future human actions.
